02 · Action Versioning
A tag is a pointer, not a version

Why @v2 Isn't a Version

  • Tags move. Anyone with write access to the action's repo can point the tag at new code. Your workflow follows it silently.
  • You can't answer "what ran?" No pinned hash means no record of the code that touched your secrets last Tuesday.
  • Updates arrive without review. A maintainer change, a compromised account, a new transitive dependency, all shipped straight into your runner.
# the less secure way: pinning to a tag
uses: tholander/actions-comment-pull-request@v2

# the more secure way: pinning to a commit SHA
uses: tholander/actions-comment-pull-request@b07c7f86be67002023e6cb13f57df3f21cdd3411

03 · Attack Patterns
No silver bullet

Common Workflow Attacks

Risk comes from two places: the code you call on (third-party actions) and the code you wrote (your own workflows). Each needs its own fix.

Pwn requests

A workflow triggered by pull_request_target checks out the fork's code but runs with the base repo's secrets and write token.

Seen in the wild: s1ngularity
Injections

A workflow passes data through shell commands, often unvalidated and open to remote code execution.

Seen in the wild: hackerbot-claw
Compromised credentials

A maintainer token or publishing credential is stolen, and the trusted action itself starts shipping malicious releases.

Seen in the wild: Trivy, KICS
04 · Case Study · Pwn Request
August 2025

s1ngularity: A PR Title That Published npm Packages

01
A PR with a malicious title was opened in the Nx repo.
02
Nx's PR-title validation workflow ran on pull_request_target and returned a GITHUB_TOKEN.
03
Malicious Nx versions shipped a postinstall script.
04
With additional creds, attackers made private repos public and exfiltrated secrets.
2,180accounts exposed
7,200repositories exposed
Lesson
The vulnerable workflow was reverted on main almost immediately. The attacker opened the PR against an outdated branch instead. Fixing forward isn't enough.
Lesson
Avoid pull_request_target whenever possible. If you have to use it, do not execute code from the PR.

hackerbot-claw: An AI Agent Hunting Workflows

An AI agent built to exploit GitHub Actions and LLM-powered workflows. It claimed to run on Anthropic's Opus 4.5 and targeted open source projects through malicious pull requests, issues, and comments between February 27 and March 2, 2026.

  2. Treat all external content as untrusted.
  3. Minimize the access.
  4. Pair prevention with detection.

10 · The Fix
Pin your dependencies

Handling Actions Versions

Pin to a full commit SHA

Pro: you choose exactly what version to use.

Con: tedious to keep current (without Dependabot), and it doesn't pin the action's own actions.

Workflow dependency locking

Pro: a lockfile covering direct and transitive actions.

Con: still in preview.

11 · The Fix
Scan the config

Let Tooling Read Every Workflow You Won't

IaC and CI/CD security rules (Datadog, Google, Microsoft, and others all ship them) parse your workflow files and flag dangerous patterns as policy violations, right in the pull request.

Triggers & permissions
Dangerous events, write-all tokens, missing top-level permissions.
Injection sinks
Untrusted context interpolated into run: steps and script arguments.
Secrets & runners
Secrets exposed to fork jobs, self-hosted runners reachable from public repos.
Unpinned references
Actions used by tag or branch. The finding that would have covered March.

Where this works, and where it doesn't

Works well
Static, syntactic patterns: an unpinned uses:, a bad trigger, an over-broad token, a raw interpolation in a shell step. High signal, low argument, fixable in one PR.
Still lacking
Intent. A pinned SHA can still be malicious code you approved by accident, and no rule tells you whether a maintainer should have publish rights. Runtime behavior needs runtime signals.
Gotchas
Reusable workflows and composite actions hide a second layer of uses:. Docker-based actions pull mutable image tags. And an "immutable release" badge doesn't stop a tag being force-pushed.

12 · Platform
Platform changes

GitHub Is Making Changes

Initial compromise
  • actions/checkout prevents checking out untrusted code from forks
  • New policies limit who triggers risky actions and which triggers are permitted
  • Actions cache is read-only for untrusted triggers
Exfiltrating credentials
  • New Actions network firewall (preview) logs all outbound traffic to detect malicious behavior
Propagating the attack
  • Dependabot has a default dependency cooldown of 3 days
  • Potentially malicious workflows are held for approval
  • Workflow-level dependency locking
  • Immutable releases
Incident response
  • Self-service credential revocation
  • Expanded credential revocation API support

13 · Takeaways
Three things, in this order

What to Do on Monday

Take inventory. Which actions do you use, and where? Which workflows hold secrets? Which repos still have a dangerous trigger active?
Start with easy wins. Start where the pattern is dangerous but the effort is small. Pin actions, adjust triggers, then widen your scope.
Make it repeatable. Put CI/CD rules in the pull request so the next vulnerability is caught by tooling, not by an attacker.

A workflow is as dangerous as code.

Review it and audit it like code.
